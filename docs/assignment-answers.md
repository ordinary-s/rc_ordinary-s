# 作业题目逐项回答

我把可靠受理、有限投递和可解释的结果作为这个 MVP 的重点。设计上的主要取舍，是接受消息可能重复、外部调用可能无法确认结果，用持久化记录和明确的终止规则控制风险。以下回答系统边界、可靠性、AI 取舍、未来演进和中间件选择；具体实现见[完整设计](design.md)，验证结果见[验收记录](verification.md)。

## 1. 系统边界：我解决什么，不解决什么，为什么

### 1.1 我把服务定位为内部 HTTP 通知投递器

上游业务方判断注册、支付、购买等事件是否需要通知，并构造外部机构要求的请求。我的服务负责接收之后的可靠保存、异步交接、有界 HTTP 执行和结果查询；广告、CRM、库存等业务含义仍由上游和外部机构解释。

我采用 Go + MySQL/InnoDB + RocketMQ + Transactional Outbox。MVP 是一个 Go 应用，内部区分 HTTP API、Outbox 发布器和 Consumer 的职责，没有仅为模块名字不同就拆成多个服务。可靠受理的边界是鉴权、校验通过且 MySQL 事务提交成功；HTTP 202 表示已受理，不能解释成外部机构已处理。

### 1.2 我选择解决的具体问题

我首先解决提交重试和消息交接。调用方身份从鉴权配置取得，`(client_id, idempotency_key)` 的 MySQL 唯一约束处理并发重复；同键同内容返回原任务，同键不同内容返回 409。通知任务与首次 Outbox 发布责任在同一事务保存，避免任务已受理却因为进程退出而没有任何发消息依据。

我接着解决重复消息下的有界执行。发布补偿与 RocketMQ 重投都可能带来重复，Consumer 读取持久化任务、尝试记录和到期时间，并在单实例内按 `task_id` 串行保护。已有终态直接结束消费，已记录的 HTTP 尝试次数不会清零。每条通知最多三次业务尝试，最终失败也留下可查结果。

我还保留最小运维能力：按调用方隔离的分页列表与详情、尝试记录、机构快速失败开关、指定失败终态的人工结论、原生 DLQ 检索，以及能串起异步任务的简短日志。数据库保存任务事实，日志帮助定位问题；这些能力支持基本排查，尚未形成完整的工单流程。

### 1.3 我明确不解决的范围

| 我不承诺或不实现的能力 | 原因与责任边界 |
|---|---|
| 调用方业务事务与通知提交跨系统原子一致 | 调用方提交前退出时，本服务可能从未收到请求。需要调用方自己的 Outbox 或其他可靠交接方式；本系统无法扫描对方业务库补齐。 |
| 任意情况下最终必达、外部副作用恰好一次 | 超时可能意味着远端已经执行；本系统也允许 FAILED、FAST_FAILED、EXPIRED、UNCERTAIN 等终止结果。MQ 不能替外部系统保证业务事务。 |
| 任意供应商适配、凭证刷新、下游动态签名和响应体业务判断 | MVP 由调用方构造请求，仅按 HTTP 结果分类。通知 API 自身使用 TLS 1.3 与 HMAC 请求签名；对下游任意供应商的签名适配与 OAuth 刷新仍需按具体契约补充。短期凭证要与排队及任务有效期相容。 |
| 严格业务完成顺序 | 有界并发、不同 HTTP 耗时和异常重投都可能改变完成顺序；幂等不能替代顺序控制。 |
| 自动熔断、半开探测、自动重放与审批后台 | 当前通过人工机构开关和结果核对控制复杂度，不为未出现的运营规模引入另一套状态机。 |
| 多实例全局配额、多机房容灾和未经测试的吞吐保证 | 当前部署和同任务内存保护面向单实例。单 MySQL、单 Broker 的本机验收不能作为 HA 或容量证明。 |

我保留 UTF-8 原始文本 Body，可用于 JSON、XML、表单与纯文本，不把二进制或 multipart 大文件作为本版能力。外部 2xx 只表示达到当前 HTTP 成功条件；例如对方返回 202，不足以证明其后台业务已经完成。“上游不用处理响应”也不等于本服务不判断并保存投递结果。

## 2. 可靠性：我如何区分消息交付、HTTP 结果和执行异常

### 2.1 我采用至少一次消息交付与有界 HTTP 尝试

我的内部消息允许至少一次交付，消费端必须处理重复。对外则采用每条任务最多三次 HTTP 业务尝试，并允许有记录地终止。这两层语义分别回答消息恢复处理与外部调用如何结束，不能合并成每条通知必达。

这个保证仍依赖数据库与 Broker 数据没有超出部署能力地丢失、消息保留策略、发布结果检查及消费确认。当前单节点开发拓扑没有覆盖任意基础设施损毁。入口幂等、消费状态检查和下游幂等是三层不同责任：只有下游真正识别同一 `task_id` 的 `Idempotency-Key`，才能帮助控制重复副作用，单纯发送该 Header 不能替对方实现去重。

### 2.2 我用 Outbox 保存发布责任

任务和 Outbox 在同一个 MySQL 事务提交，API 在提交成功后才返回已受理。发布器只扫描到期且 `publish_state=PENDING` 的 Outbox，在数据库长事务外发送 RocketMQ，`SendSync` 返回 `SendOK` 后才写 `PUBLISHED`。

发送未确认或本地发布标记失败都会保留补发责任，并尝试写入发布退避时间；如果这次写入也失败，下次扫描仍可能立即重发。Broker 已接收但本地未记成功时同样可能重复发布，因此稳定的 `event_id`、`task_id` 和消费状态校验不可缺少。Outbox 只解决消息发布，不负责重新执行已经终止的 HTTP 任务；两者的次数也独立管理。

### 2.3 我对临时 HTTP 失败只给三次总机会

三次包含首次，因此最多只有两段业务退避。我默认采用指数退避并加入少量抖动，避免临时故障时立刻连续请求下游。单次请求、取得任务锁后的处理过程和任务有效期各有时间上限，限制重试占用 Worker 的时间；等待任务锁的时间尚未纳入处理预算。具体默认值见[设计中的 HTTP 重试配置](design.md#8-每个任务最多三次-http-业务尝试)；这些是实现初值，尚未通过容量压测调优。

我把 429 和 5xx 作为当前可继续尝试的 HTTP 状态，其余非 2xx 状态提前保存 FAILED，2xx 保存 DELIVERED。第三次可重试失败同样保存 FAILED，随后结束消费。三次是上限，不要求每种错误都把次数用满；第一次永久失败、到期、快速失败或结果不明都可以更早结束。

如果下游通过有效的 `Retry-After` 要求更长等待，我取它与本地退避中的较长者；剩余时间不足则终止为 FAILED。我把下次允许发送的时间与本次尝试结果一起持久化，避免进程中断或消息重投绕过退避。每轮发送前重新检查终态、有效期和机构开关，等待可以取消；重投不会重置次数或延长截止时间。

我区分启动过的业务尝试和实际网络发送次数。尝试启动事务先于 HTTP，启动后进程退出也保守消耗该次机会。Go HTTP Transport 对部分请求可能有内部重试，现有三次业务上限与可计数 mock 场景不能证明任意故障下供应商只收到三次网络请求。

### 2.4 我在结果可靠保存后才结束消费

| 我观察到的情况 | 我保存或保留的依据 | 消费行为 |
|---|---|---|
| HTTP 2xx | DELIVERED 与尝试结果 | 保存成功后返回消费成功。 |
| 次数耗尽或永久失败 | FAILED 与原因 | 结束消费，不重新发布业务任务。 |
| 机构开关开启 | FAST_FAILED | 不启动新的 HTTP，保存后结束消费。 |
| 已过期或远端结果不明 | EXPIRED 或 UNCERTAIN | 保存后结束消费，停止自动 HTTP。 |
| 重复消息对应已有终态 | 保持原结果 | 不增加 HTTP 次数，结束重复消费。 |
| 数据库读取、结果保存或执行上下文等未可靠完成 | 已有任务和尝试记录 | 返回 `ConsumeRetryLater`，由 RocketMQ 原生重试恢复。 |
| 原生异常重试耗尽 | Broker 的 DLQ 消息及可关联任务 | 人工排查，不建立第二套应用异常发布队列。 |

我把结果保存重试与 HTTP 重试分开。HTTP 返回后，优先有限次重试保存已有结果，避免因写库失败再次调用外部系统；仍无法保存才返回执行异常。恢复时若发现未完成的 STARTED 尝试，系统将尝试标为 UNKNOWN、任务标为 UNCERTAIN，并停止自动发送。具体保存次数和等待参数见[设计](design.md#8-每个任务最多三次-http-业务尝试)。

连接错误或 HTTP 超时同样可能是远端已执行，当前实现保守转 UNCERTAIN。若整个处理上下文已取消，或读取响应过程未完成，先返回执行异常，后续通过未完成尝试恢复到 UNCERTAIN。这可能放弃部分原本安全的重试机会，代价是增加人工核对，但能降低重复副作用的风险。MySQL 写入故障、重复消费及 SIGTERM 的验证结果见[验收记录](verification.md)。

### 2.5 我用机构级人工快速失败处理长期不可用

负责人确认某机构长期故障后，由管理员开启该机构的 `fast_fail_enabled`。非终态任务在发送前读到开关，就保存 FAST_FAILED 并结束消费，不等待外部超时，也不排队等待恢复。开关不能撤销已经发出的请求，检查与实际发送之间也不是跨网络原子操作；当前共享 Worker 仍可能让其他机构承受慢请求的资源影响。

一条通知三次失败得到的是该任务的 FAILED，不会自动开启整个机构开关。单条参数错误不足以证明机构整体故障。恢复需要负责人依据对方通知、已有监控或安全人工验证确认，再关闭配置；关闭后只有仍有发送资格的非终态任务和新任务能发送，旧 FAILED/FAST_FAILED 不会复活，次数也不重置。

我选择终止式快速失败，因此已经受理的通知也可能一次 HTTP 都不发。它能限制持续故障的执行开销，代价是需要向调用方披露不会自动补送，并由人工决定后续业务动作。当前没有错误率阈值、半开探测或自动恢复能力。

### 2.6 我保留可操作但有限的人工与日志闭环

负责人可以查询任务和尝试，在核实外部状态后对 FAILED、FAST_FAILED、EXPIRED、UNCERTAIN 保存文字结论、操作人和时间。resolve 不改变业务状态、不增加预算，也不是核实成功后改成 DELIVERED。DLQ 单独查询，按 `task_id` 核对；它不会自动建数据库工单，消息也不是永久保存的业务档案。

resolve 不接受仍处于 PENDING/PROCESSING 的任务，因此这类 DLQ 消息需要人工核查并在应用外记录结论，尚不能在应用内完成处置。当前也没有自动搬运、人工 replay 接口或审批平台。具体影响见[已知限制](implementation-review.md)。

日志用任务持久化的 `trace_id` 和稳定 `task_id` 关联 API、Outbox 小消息与消费执行，核心结果日志附机构、尝试数、结果、码和耗时。字段在调用时显式传递，不在共享可变 logger 上写当前请求状态。关键结果与必要异常简短输出，尝试表记录处理依据，不打印正文、完整 Header、Token 或响应全文，也不增加无界日志队列。部分异常路径仍缺关联字段，启动和 SDK 日志的脱敏验证也不完整，详见[已知限制](implementation-review.md)。

## 3. AI 取舍：哪些建议没有采纳，我为什么这样选择

### 3.1 未采纳的方案及其原因

面对 AI 提供的方案，我关注两个问题：它解决了哪个具体故障窗口，以及需要增加多少实现和运维成本。事务、唯一约束和结果持久化有明确作用；自动熔断、分布式协调和完整重放平台则需要更充分的业务依据。主要取舍如下，详细理由见[决策记录](decisions.md)，AI 辅助范围见[AI 使用说明](../AI_USAGE.md)。

| 方案 | 项目的选择及我的判断 | 我接受的代价 |
|---|---|---|
| PostgreSQL | MySQL/InnoDB 已具备事务、唯一约束与索引能力，当前没有依赖 PostgreSQL 专属功能的需求。 | 需验证 SQL、隔离、排序规则与查询计划。 |
| Java/Spring AOP、事务事件组织入口 | Go 标准库与显式组合；公共逻辑和应用事务清楚分工，不移植注解代理体系。 | 公共能力的接入需要显式维护。HTTP 与 MQ 两个入口都要接入必要的关联信息和执行逻辑；新增调用路径可能遗漏这些行为。 |
| RocketMQ 或 Spring 事件直发链 | RocketMQ 为唯一 MQ 主路径；普通内存事件不承担持久发布责任。 | 相较只用数据库和进程内事件，多了一套需要部署、监控和恢复的 Broker 依赖。消息系统不可用时，Outbox 会积压，投递时间随之增加。 |
| 整批确认，再把失败单条手工发布 | 单条回调和有界并发，避免批次部分失败与再次发布的额外原子性协调。 | 暂不利用批量消费提高吞吐，后续根据压测瓶颈再评估。 |
| 首次加三次，业务失败后继续入队 | 最多三次总 HTTP 尝试，可靠保存终态后结束消费；仅执行异常走原生重投。 | 终止后不会无限追求送达，调用方必须接受契约。 |
| Properties 维护另一套异常次数及重试队列 | 使用 RocketMQ 原生有限重试和 DLQ，持久化 HTTP 预算独立管理。 | 异常恢复策略受所选版本与消费模式约束。 |
| 暂停后补送、完整自动熔断和半开平台 | 人工机构开关，FAST_FAILED 是终态；自动化留待真实需要。 | 判断故障、确认恢复依赖人工，历史终态不自动补发。 |
| Redis 锁、CDC、分布式事务、独立调度与日志平台 | 保留本地事务 Outbox、唯一约束、单实例执行保护和轻量日志。 | 多实例协调与运营能力有限，需要明确边界。 |

### 3.2 我没有为了简化而删除可靠性基础

Outbox 对应已受理但尚未可靠发消息的窗口；唯一约束对应并发重复提交；持久化尝试、终态和退避对应重投与中断恢复；结果先保存再确认对应消费责任交接；超时、并发和连接上限对应资源耗尽。它们都有可说明的失败场景，我保留这些机制，而不是单按组件数量评价复杂度。

这些机制分别处理不同的风险：结果保存重试处理暂时写库故障，UNCERTAIN 处理无法确认的外部副作用，Outbox 退避控制发布补偿频率。将它们分开，可以避免一次数据库故障意外触发新的 HTTP 调用，也更容易定位和验证问题。

我接受消费内等待占用 Worker、人工恢复速度依赖人、单实例不能横向协调等限制。扩容前先找到真实成本，比一开始建设多级重试框架更容易解释和验证。

## 4. 未来演进：我如何按流量与故障证据增加能力

以下是尚未实现的演进方向。现有投递流量控制主要依靠消费并发与 HTTP 连接上限，没有调用方入口限流、按机构令牌桶、独立投递组、多实例全局配额或自动熔断。我会根据实际流量和故障指标逐步增加这些能力。

### 4.1 我先限制上游接收量与外部实际发送量

入口按调用方身份限制持续速率、突发量和待处理量，避免一个业务方挤占所有受理与存储资源。超额请求应在受理事务前明确拒绝，并约定调用方用原幂等键退避重试；已受理任务不能因为后来限流就悄悄丢失。入口限流保护本系统，不能代替外部机构配额。

出口按外部机构或共享账号的实际限额设置令牌桶：按许可速率补充令牌，发起一次业务尝试消耗一个令牌，桶容量限制突发。首次与两次 HTTP 重试共用额度，不给重试单独免配额；取不到令牌时还没启动 HTTP，不消耗尝试次数，但任务有效期继续流逝。等待必须可取消，时间不足时按明确策略结束，不能用不断返回消费失败来伪装限流。

QPS 与同时在途请求数要分别限制。即使平均速率不高，慢响应也能堆积连接和 Worker；我会给机构设置独立在途上限，在完成或取消时释放名额。令牌控制每段时间开始多少次，在途限制控制同时占用多少资源，二者需要配合。具体阈值依据下游契约、实际延迟和测试确定，目前尚无经过验证的机构 QPS 配置。

多个接口若共享同一供应商账号，就共享总额度，不能每个 URL 都获得全部配额。RocketMQ 拉取批量与缓存上限只控制消息取得和缓冲，不能当作 HTTP 每秒速率限制。

### 4.2 我按机构和重要性分组，同时隔离执行资源

低流量机构先共用默认组；当某机构高流量、长延迟、故障频繁，或某类业务有更高时效要求时，再划分投递组、Topic/队列分配和独立 Worker 配额。RocketMQ 的不同消费组会分别消费订阅的消息，因此机构分流还需要明确路由和订阅关系，不能只靠增加消费组完成。

只拆队列但继续使用同一个无约束执行池，慢机构仍然可能占满全部 Worker。我会同时划分连接池、在途上限、速率额度和必要的发布/消费容量，让故障影响有实际资源边界。优先保护关键业务，也要给普通组保留最低资源，防止长期饥饿。第一版不为每家机构部署一个微服务。

### 4.3 我在人工保护不足时再评估自动熔断

现有人工开关适合可控规模。故障频繁且人工反应时间不能满足需求时，我才加入机构级连续失败或错误率判断、冷却时间、少量半开探测和受控恢复。判断需要区分网络/服务错误与单条请求参数错误，避免一个无效请求触发整个机构停止。

自动化不会自然改变 FAST_FAILED 的终止语义。若未来需要暂缓并恢复补送，必须另行设计状态、有效期、容量和授权契约；不能只把人工开关改成自动开关，就复活旧任务。探测同样受机构配额和资源上限约束，恢复时避免积压瞬间冲击对方。

### 4.4 我在多实例前先确定执行权和总额度

当 API、Publisher、Consumer 的负载不同，我会分别部署和扩容。单纯复制当前进程并不安全：内存同任务锁不能跨实例共享，Outbox 扫描也需要明确领取/归属策略，机构额度不能随副本数量倍增。这些前置条件与具体风险见[已知限制](implementation-review.md)。

机构流量稳定时，可先用明确任务归属或固定额度分配，保证各实例合计不超限；若动态扩缩容确实需要共享额度，再评估协调组件和故障行为。我不会在缺乏规模证据时先引入 Redis 锁或分布式限流平台。

### 4.5 我用指标决定扩哪里

| 我观察的信号 | 我会先排查或采取的方向 |
|---|---|
| API 延迟、数据库事务等待、连接池耗尽 | 检查事务时长、索引、SQL 和接收负载；确认瓶颈后扩 API/数据库能力。 |
| 待发 Outbox 数量与最老记录年龄持续上升 | 检查 Broker 可用性、发布速度和扫描执行计划，再决定发布器容量。 |
| MQ 积压增长，本地 Worker/CPU/连接饱和而下游还有额度 | 改善消费效率，再增加隔离后的 Consumer 资源。 |
| 429、下游高延迟或超时增长，机构额度已经用满 | 限制出口、入口削峰、调整业务时效或协商配额；增加 Worker 不会提高许可发送量。 |
| 某机构拖累其他机构 | 检查共享执行池和连接资源，实施机构或重要性分组隔离。 |
| 历史任务/正文与索引持续增大 | 先做实际执行计划优化、批量清理与归档，分别定义正文和幂等依据保留期，再评估分库分表。 |

我同时观察执行异常、DLQ、UNCERTAIN 和人工待核对年龄，而不是只看平均 QPS。聚合指标不要求每条任务打印更多日志，也不能用一次本机 Docker 通过替代持续容量监控。

## 5. 中间件选择：为什么用，不用时怎样替代

### 5.1 我选择 Go 来保持实现与部署直观

项目采用 Go，以 `net/http`、`database/sql`、`log/slog` 和显式依赖组织 API、事务、发布与消费。对这个单应用 MVP，我看重的是控制流清楚、依赖少，便于检查取消和错误分支。Java/Spring Boot 等框架同样可以实现这些责任；可靠性取决于事务边界和恢复机制，而非语言本身，因此当前也没有额外移植 AOP 代理体系。

### 5.2 我用 MySQL/InnoDB 保存可恢复的事实

任务、入口幂等依据、尝试结果和 Outbox 都需要事务与唯一约束，并需要按调用方、状态和时间查询。MySQL/InnoDB 已满足这些要求，表结构采用明确排序规则与 UTC 时间。PostgreSQL 等事务数据库也可替代，代价是迁移 SQL、索引、驱动和验证，而不是业务设计必须推倒重来。两者都不能单靠品牌解决外部 HTTP 副作用原子性。

若完全不用事务数据库，就要为幂等、结果查询与发布责任找等价的持久化和原子机制；仅在内存保存任务不足以满足进程退出后的恢复要求。

### 5.3 我用 RocketMQ 承担分发与消费异常恢复

RocketMQ 提供消息分发、消费重投及 DLQ，使 HTTP Consumer 不必自行实现完整的持久任务调度器。代价包括运行 Broker/NameServer、固定 SDK 组合、配置 Topic/Group、理解通告地址和消费超时，以及维护真实重试/DLQ 操作流程。

RabbitMQ 是可行替代，但确认、路由、重试及 Go 客户端需要重新设计和验证，迁移并非只替换组件名称。若不用 MQ，可以用持久任务表加数据库扫描，不过需要自行承担领取、并发控制、中断恢复、异常重试和堆积运维；普通内存事件无法替代可靠队列。

### 5.4 我保留 Transactional Outbox 来处理本地双写窗口

Outbox 是把业务记录与发布责任放进同一本地事务，再异步发消息的模式，不是必须接入的 AWS 产品。先提交数据库再发 MQ，进程可能在两步之间退出；先发 MQ 再提交数据库，消费者可能看不到已提交任务，或任务随后回滚。轻量扫描器让这些窗口有持久恢复依据，同时接受重复消息并在消费侧处理。

替代办法包括重新定义为 MQ 首次可靠受理、采用其他可靠事件机制，或在有明确需求时使用 CDC/事务消息；它们需要重设响应、查询、一致性和运维契约。直接删除 Outbox 而仍宣称数据库与消息可靠原子交接，不是等价替代。Outbox 本身也不能保证外部恰好一次，更不承担终止 HTTP 任务的重新调度。

### 5.5 我用 Compose 和短日志让交付可复现

Docker Compose 固定依赖版本并运行应用、真实 MySQL、RocketMQ 与可计数 mock target，降低手工安装差异。手工运行同版本依赖也可行，但要自己保证配置和生命周期一致；容器启动成功仍不等于端到端场景通过。实际命令、退出码和未覆盖范围统一见[验收记录](verification.md)。

日志用于关联关键结果，数据库用于保存任务和尝试事实。当前通过短日志和关联 ID 支持排查，需要更大规模观测时再补充指标和集中检索。这样保留了基本定位能力，也避免为 MVP 增加独立日志服务和完整追踪平台的维护成本。
