# 作业题目逐项回答

以下按作业 PDF 的问题次序回答。作业 PDF 的要求是问题与交付形式；Go、MySQL、RocketMQ、三次业务尝试和 Docker 实测是用户补充后确定的实现约束。

## 1. 系统边界：解决什么、不解决什么

我把系统边界放在“调用方请求已通过本服务鉴权、校验且 MySQL 事务已提交”之后。服务实现可靠受理、调用方幂等、notification 与 Outbox 原子保存、异步发布、有限 HTTP 投递、机构快速失败、终态查询和人工处置结论，代码在 `internal/api`、`internal/notification`、`internal/store`、`internal/outbox`、`internal/mq` 与 `internal/delivery`。

我不承诺调用方自己的业务事务提交之前绝不丢通知；跨调用方业务库与本系统的原子事务不在边界内。若调用方必须把通知与其业务变更原子化，应由调用方自身使用 Outbox 或其他可靠交接方式。

我不承诺外部业务恰好一次。RocketMQ 允许重复投递，网络超时可能是远端已执行而本地未知，下游需真实支持相同 task ID 的幂等键。MVP 不能替任意供应商解释业务响应、刷新凭证、维持严格全局顺序或证明远端最终执行。

## 2. 可靠性和失败处理

内部 MQ 消息允许至少一次交付，消费端根据任务状态和已保存的 HTTP 尝试恢复。一次通知最多三次 HTTP 业务尝试，包含首次；MQ 重投不会清空计数。2xx 保存 DELIVERED，永久 4xx 保存 FAILED，可重试 429/5xx 最多用完三次后保存 FAILED。过期保存 EXPIRED，机构开关开启保存 FAST_FAILED。上述结果可靠保存后都返回消费成功，不把业务失败作为另一条 MQ 任务重发。

只有任务读取/结果保存失败、数据库故障、上下文取消等导致本次流程没有可靠完成时才返回 RocketMQ 原生重试。选定版本的消费者配置有限 `MaxReconsumeTimes`；耗尽后进入该消费组 DLQ。DLQ 是运维人工核对入口，MVP 不把它自动同步成数据库待办。

HTTP 连接错误/timeout 可能表示远端已执行，所以我保守写 UNCERTAIN，避免无依据重发。外部 HTTP 成功后，结果写库在同一次消费中最多重试 3 次（首次加两段短等待），仍失败才由 MQ 原生机制重投；这段重试只保存结果，不再发送 HTTP。真实 MySQL trigger 验证了三次结果保存失败后 RocketMQ 重投，恢复时将 STARTED 标为 UNKNOWN、任务标为 UNCERTAIN，mock 仍只有一次 HTTP 请求。attempt 结果与 notification 更新在同一事务。下游若没有实现幂等，本系统无法消除所有“远端成功、本地未知”的副作用风险。

Outbox 与 notification 在同一事务创建。发布成功确认后才标记 PUBLISHED；未确认保留发布责任并退避补发。确认丢失可以产生重复消息，因此消费者幂等仍必要。定时扫描只补发 Outbox，不扫描所有投递失败任务。

长期不可用时，管理员显式开启机构 fast-fail。开关只对之后进入处理且仍非终态的任务生效；FAST_FAILED 是有记录的终止放弃，不表示已送达，也不是等待恢复的排队状态。人工确认恢复并关闭开关后，新任务可继续投递，旧终态不会复活。单条参数错误不自动打开机构开关；本项目没有自动熔断/半开探测。

由于有终止失败、快速失败、过期和结果不明，本系统不保证每条通知最终必达，也不保证外部恰好一次。

## 3. 取舍与演进

我没有采用早期四次 HTTP 尝试、业务失败重新发布、批次成功/失败单条协调、RabbitMQ 与 RocketMQ 双路、自动熔断或长时间快速失败暂存。最终方案是最多三次总 HTTP 业务尝试、单条消费和有界并发、业务终态成功确认、执行异常由 RocketMQ 原生重试；外部成功后的结果保存另有有界数据库重试，不消耗 HTTP 预算。代价是快速失败会终止任务，恢复后要由人工核对/授权后续业务动作；MVP 不自动重放。

如果流量增长，我会先按调用方做入口配额；按机构/共享账号做出口速率和在途并发限制，HTTP 重试也占相同额度。按流量、延迟和重要性分组，必要时给慢机构专用 Topic/Worker 资源降低互相挤占。仅拆队列不等于完全隔离，MQ 拉取批量或缓冲上限也不是 QPS 限速。

观察到真实瓶颈后，再把 API、Publisher、Consumer 分开部署，协调全局配额、完善故障隔离、自动熔断、按策略归档。以上都是后续设计，当前不包含 Redis、集群租约、配置中心或管理后台。

## 4. 中间件选择与替代路线

Go 是本项目语言选择，不是作业规定。`net/http`、`database/sql`、`log/slog` 与显式依赖注入保持部署和控制流较直观；不为模仿 Spring 引入 AOP/注解分层。

MySQL/InnoDB 用于事务、唯一约束、任务查询与 Outbox；不是因为它天然比 PostgreSQL 可靠，而是当前模型只需要常规事务、索引、约束和 JSON/二进制字段，没有 PostgreSQL 专属能力要求。PostgreSQL 也是可行事务数据库替代。

RocketMQ 用于持久排队、分发、消费重投和 DLQ。成本是要运行 Broker/NameServer、配置 Topic/Group、理解原生重试和网络通告地址。RabbitMQ 是早期候选，但最终没有并存。若不使用 MQ，可用持久化任务表/事件表加数据库扫描，但需要自行负责领取、并发、超时、重投与堆积运维；普通内存事件不能作为可靠队列。

Transactional Outbox 是“业务记录与发布责任本地事务保存，再异步补发”的模式，不是 AWS 产品。没有 Outbox 时，先提交数据库再发 MQ 会有提交后漏消息窗口；先发 MQ 再提交会有消费者读不到已提交任务或任务回滚窗口。
