# 作业题目逐项回答

题目来源为用户提供的两页作业 PDF。以下按题目关注的系统边界、投递语义、失败处理、AI 设计取舍、演进和基础设施选择逐项回答。Go、MySQL、RocketMQ、TLS/HMAC、目录位置和 Docker 真实验收是后续讨论确定的实现约束，不是 PDF 指定的技术栈。

## 1. 系统边界：我解决什么，不解决什么

### 1.1 我解决的问题

我把服务定位为一个异步 HTTP 通知投递器。上游在自己的业务事务中记录待发事件，并把完整的版本化通知事件投递到 RocketMQ。本服务负责消费事件、校验版本和目标、将通知先持久化到 MySQL、按有限预算调用外部 HTTP、保存状态、提供查询和最小人工核对能力。

接收身份来自部署配置，而不是事件正文。相同 client_id 和 event_id 只对应一项逻辑通知；相同事件重复到达且业务字段一致时复用数据库任务。业务内容不同的冲突事件不会覆盖旧数据，也不会调用 HTTP。

我还负责在机构快速失败打开时终止后续任务、记录失败原因；对执行异常使用 RocketMQ 原生重试和 DLQ；提供按客户端隔离的查询、管理员开关和人工核对结论。

### 1.2 我不解决的问题及原因

| 不解决的能力 | 原因与责任边界 |
|---|---|
| 上游业务事务与本服务跨库原子提交 | 本服务不参与上游数据库事务。上游必须用自己的 Outbox 或等价机制保证业务提交到消息发布的可靠交接。 |
| 每条通知最终必达 | 允许 FAILED、FAST_FAILED、EXPIRED、UNCERTAIN 和 DLQ。有限资源与人工终止意味着系统不承诺所有消息一定发送成功。 |
| 外部业务恰好一次 | HTTP 超时可能发生在远端已执行之后；本地数据库和外部机构之间没有共同事务。下游只有实际按稳定 task 幂等标识去重时才可能抑制部分重复副作用。 |
| 严格顺序 | 并发消费者、外部响应差异和 MQ 异常重投都会影响完成顺序。本版没有按业务键串行的持久化调度。 |
| 任意供应商适配、动态凭证刷新与业务响应解析 | 这些能力依赖各供应商契约，超出通用 HTTP 投递 MVP。本版使用目标白名单、常见 HTTP 方法和原始 UTF-8 文本，不解析供应商业务正文。 |
| 多实例全局限流、高可用及机器损坏零丢失 | 验收拓扑是一个应用、一个 MySQL 和单 Broker，不能据此推导多实例协调、容灾或容量保证。 |
| 自动熔断、半开探测、终态自动重放和审批平台 | 机构开关由管理员明确设置；开关触发的是终止结果，不是暂停队列。恢复后旧终态不复活。当前没有自动探测与授权重放流程。 |

请求 Body 保持 UTF-8 原文，可透传 JSON、XML、表单和纯文本，不支持 multipart 或大文件。下游 HTTP 2xx 只表示本服务当前 HTTP 成功条件满足，不证明对方后台业务已完成。

## 2. 可靠性：我采用什么投递语义，如何处理失败

### 2.1 投递语义

RocketMQ 内部按至少一次交付设计，所以事件可能重复。消费端的唯一键、指纹和终态检查用于重复安全。外部 HTTP 每个 task 最多有三次业务尝试，包含首次和最多两次重试。两者是不同预算：MQ 重投不会重置 HTTP 尝试数。

DELIVERED、FAILED、FAST_FAILED、EXPIRED、UNCERTAIN 只要可靠保存就结束消息消费。只有读取、保存等执行流程未完成或结果未可靠持久化，才返回消费失败交给 RocketMQ 原生有限重试；耗尽后进入该版本对应的 DLQ。DLQ 不自动生成数据库人工待办。

因此，我不承诺通知最终必达或外部业务恰好一次。下游不支持幂等时，远端成功而本地结果未知仍有重复副作用风险。

### 2.2 外部临时失败和长期不可用

对于可重试的 HTTP 429/5xx，我使用最多三次业务尝试和两段退避。达到上限后保存 FAILED 并确认消息，不再新发布业务任务。不可重试响应可以提前终止。有效 Retry-After 不能被提前绕过；如果剩余处理预算或任务有效期不足，则停止自动重试。

任务有明确绝对 UTC expires_at。到期后不启动新请求并保存 EXPIRED。机构长期不可用时，管理员开启 MySQL 中的 fast_fail_enabled，后续任务不发 HTTP，保存 FAST_FAILED 后完成消费。确认恢复后管理员关闭开关，只有后续仍可执行的任务受影响；已经 FAILED 或 FAST_FAILED 的任务不会自动复活。

本版不根据单任务失败自动暂停整个机构，也没有自动熔断、半开探测或定时恢复队列。这样控制状态机复杂度，但长期不可用期间的恢复判断依赖人工。开关不能撤销已经发出的请求，读取开关到网络发送之间也有很短的并发窗口。

### 2.3 结果未知与异常恢复

事件先落 MySQL 再开始 HTTP。HTTP 已成功但结果写库失败时，当前处理优先有限重试保存既有结果，不直接重新调用 HTTP。若进程在请求前中断，未启动尝试的 PENDING 任务可以在重投后继续；若记录中有 STARTED 尝试，远端执行可能已发生，恢复时保存 UNCERTAIN/UNKNOWN 并停止自动发送。

服务返回执行异常时由同一条 MQ 消息的原生重投负责恢复，不另发一条异常消息，不再以 Properties 或数据库计数实现第二套重试。RocketMQ 的实际重投间隔和 DLQ 进入条件随所选 SDK、Broker 配置而定，验收通过真实容器等待核实。

### 2.4 上游事件的幂等边界

上游必须稳定复用 event_id，不能每次发布都生成新 ID。服务用配置中的可信 client_id 与 event_id 唯一约束；指纹包括目标、规范化 method/header、原文 body 和绝对到期时间，排除 trace_id。冲突时不覆盖也不发送，原生重试耗尽后进入 DLQ。上游应将修正后的业务内容视为新的明确事件，并保留人工处置记录，而不是复用同一 ID 修改事件内容。

## 3. AI 设计取舍和未来演进

### 3.1 我收敛或未采用的早期建议

| 早期方向/过度设计 | 最终处理 | 理由和代价 |
|---|---|---|
| Java/Spring AOP 式注解和隐式事务组织 | 最终使用 Go、标准库和显式依赖 | MVP 需要清楚看见 context、事务与错误边界；代价是显式编排需要更仔细维护。 |
| RabbitMQ + Spring 事件路线 | 替换为 RocketMQ 直接消费主路径 | 不保留两套 MQ/发送系统；代价是学习并验证 NameServer、Broker 路由和 Go SDK 原生重试。 |
| 本服务接收 HTTP 通知并写内部 Outbox 发布 | 按讨论后的 MQ 接入要求移除 | 上游业务与其 Outbox 才是本系统入口；本服务只持久化消费到的事件。代价是上游必须承担自己的业务 Outbox 和消息发布责任。 |
| 批量部分确认再协调失败单条重发 | 使用单条回调和有界并发 | 错误对应一条逻辑通知，确认边界直观；代价是批量吞吐优化没有实现。 |
| 首次加三次重试 | 明确为总共三次，即首次加两次重试 | 按业务预算定义，避免把上限理解成四次。 |
| HTTP 最终失败重新入队，或所有 error 都重发 HTTP | 终态业务结果 ACK；仅执行异常走 MQ 重试 | 防止 HTTP 业务失败无限重放以及 MQ 重投重新获得完整 HTTP 预算。 |
| 把快速失败任务暂停排队，开关关闭后自动恢复 | 记录 FAST_FAILED 终态，管理员只影响后续任务 | 避免隐含恢复重放；代价是旧失败任务需人工处理。 |
| 自定义 Properties 异常计数并手工重新发布 | 使用一套 RocketMQ 原生重试与 DLQ | 减少两套计数/发布路径的一致性问题；恢复时间取决于 Broker 策略。 |
| Redis 锁、多实例租约、自动熔断/半开、第二套重试队列、完整审批/日志平台 | MVP 不实现 | 当前没有对应的多实例、流量或运营证据；代价是单实例边界和人工处理仍需接受。 |
| 为请求体额外自创加密 | 用 TLS 1.3 保护链路，API 按需使用标准 HMAC 签名 | HMAC 不加密；自定义加密会增加密钥交换和轮换负担。 |

### 3.2 流量或复杂度增长后的路线

如果流量增长，我会先按上游 client 限制入口，再按机构或共享账号设出口速率和在途并发。首次尝试和重试共用同一机构额度，避免重试流量绕过配额。

我会按机构的流量、响应速度、业务重要性及供应商共享账号分组。若慢机构占满公共 Worker，再给关键或高风险机构安排独立 Topic/队列和 Worker 资源；单独拆队列但继续共用同一线程池并不构成隔离。MQ 批量和预取上限只控制缓冲，并不等同 QPS 限流。

确认瓶颈后再分别扩容 API、消费者或 Publisher（本版没有 Publisher）。增加消费者实例前，先解决同 task 跨实例执行权、全局机构配额、熔断恢复以及连接资源配额。更后续再按真实数据评估自动熔断、数据归档和独立运行单元。Redis、配置中心、Kubernetes、管理后台及这些扩展都没有为了写演进答案而塞进 MVP。

## 4. 中间件及替代路线

### 4.1 Go

我选择 Go 是实现语言决策，不是参考项目强制要求。Go 标准库的 net/http、database/sql、log/slog 加少量明确依赖足以实现这个边界。可替代语言包括 Java/Spring、C# 或 Rust；若团队更熟悉对应生态也可实现相同契约。选择 Go 的代价是项目要自行显式编排生命周期、错误和事务，不能把语言选择误说成性能已被压测证明。

### 4.2 MySQL/InnoDB

我用 MySQL 保存事件、入口去重依据、HTTP 尝试、目标开关和人工结论；事务与唯一约束让同一事件只创建一个任务。当前没有 PostgreSQL 专属能力需求。PostgreSQL 也是可行事务数据库替代，但切换需要重验证驱动、SQL、collation 和迁移。MySQL 并不天然比其他事务数据库更可靠，正确性依赖约束、事务边界、备份和运行维护。

### 4.3 RocketMQ

RocketMQ 用于上游事件排队、Consumer 分发和执行异常原生重试/DLQ。选择它后依赖 NameServer、Broker、Topic/Group、容器通告地址和与 Broker 配套的 Go SDK，并需承担运维成本。RabbitMQ 也是可选消息系统，早期路线已被替代；不能把其确认或 Java SDK 配置复制成 RocketMQ Go API。

若不使用独立 MQ，可将持久任务表加数据库扫描和领取/恢复逻辑作为替代；这会自行承担轮询、抢占、并发协调和死锁恢复。普通内存 channel 不是进程退出后可靠队列。

### 4.4 上游 Outbox 与本服务边界

Transactional Outbox 是上游用自己的业务事务保存发布责任的一种模式，不是本项目引入一个 AWS 产品。若上游先提交业务库再独立发 MQ，两个动作之间中断会漏通知。若上游没有 Outbox，则需接受该双写风险或由其持久任务表扫描补偿。本服务不替上游访问其业务库，也不维护第二份通知发布器。
