# 实现审查与已知限制

本页按当前 MQ 直入代码整理，不沿用旧版 HTTP 提交 / 本地 Outbox 发布方案。完整边界见[设计说明](design.md)，Docker 实际覆盖与未执行项目见[验收记录](verification.md)。

## 已实现并验证的保护

- 上游事件必须满足 schema v1、UTF-8、体积上限、目标 allowlist 和绝对 UTC 截止时间；可信 client_id 来自配置。
- 同 client_id + event_id 通过 MySQL 唯一约束和 SHA-256 指纹避免重复创建；相同 ID 的不同内容被拒绝并转入 Broker 原生失败重试/DLQ。
- notification 在 HTTP 请求前落库；异常恢复不把 HTTP 业务预算清零。
- 终态结果保存后结束 MQ 消费；数据库/执行流程未完成时才返回原生重试。
- Compose 中 TLS 最低 1.3，API Bearer 与 RFC 9421 HMAC/nonce 验证真实测试通过；管理员和客户端 key 区分。
- mock target 仅为测试配置允许的目标，重定向关闭，HTTPS 验证服务器证书。

## 已知限制

| 限制 | 影响 |
|---|---|
| 单实例内存 task 锁 | 保护本进程内并发重复消费；多个实例之间没有共同执行权协调。 |
| 精确 MQ commit/ACK 故障窗口未注入 | 重复终态消息证明持久状态去重，但没有让进程恰好在终态 DB commit 后、Broker ACK 前崩溃。 |
| SIGTERM 覆盖 HTTP 在途场景 | 当前真实停启验证得到 UNCERTAIN 且只有一次 HTTP；没有独立的进程终止测试覆盖所有调用前/commit 后指令窗口。 |
| 快速失败是人工终止设置 | 开关只影响观察到它之后的任务；不能撤回已经发出的请求，也不是自动熔断或全局速率控制。 |
| DLQ 不自动成为数据库待办 | 需用 mqadmin 查询/导出；损坏事件可能没有可查询 task_id，负责人应在外部受控处置记录中登记。resolve API 只对符合条件的数据库终态记录保存结论。 |
| 管理员身份来自静态配置 | 当前 ADMIN_ACTOR 和 key 配置代表单个配置管理员，没有多人身份目录或不可变审计流水。 |
| 旧 Outbox 表仍在 migration | 用于保留旧部署历史；新版不插入、不扫描、不发布。切换前需排空旧版本并核对旧表中 PENDING 记录，不能简单启动新旧版本一起消费。 |
| 应用数据未做字段级静态加密 | TLS/HMAC 保护 API 传输与完整性，notification body 在 MySQL 中仍是服务可读数据；生产需依赖磁盘/数据库存储安全策略。 |
| 三次业务尝试不等于所有网络故障物理发送次数 | 业务次数记录本地启动的 HTTP 尝试。Go Transport 对特定连接失败可能透明重试；项目不自建 HTTP 协议栈。 |
| 无生产容量/多实例验证 | Docker 结果只证明固定开发拓扑功能路径，不构成吞吐、HA、RPO/RTO 或公网安全审计结论。 |

## 后续方向

按实际流量和机构 SLA 增加机构出口配额、隔离执行资源和多实例一致执行权；按 DLQ 处置需求增加受控人工登记/重放流程；按存储要求制定数据保留和归档。以上均是后续设计，当前不通过复杂状态机提前实现。
